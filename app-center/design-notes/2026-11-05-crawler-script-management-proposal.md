# App Center 平台爬虫配置：独立版本、审核、分发与应用审核依赖

状态：`SUPERSEDED`（前期讨论存档，以下保留当时的提案语境）。服务归属于 2026-11-05 确认；2026-11-06 用户接受 UC-APP-041–049 与 ADR-008。当前决定和实施顺序统一见[已接受的脚本用例清单](2026-11-05-crawler-script-use-case-review.md)，以相应用例与 ADR 为准。

## 已确认的范围

1. 这是**平台维护的爬虫脚本/配置文件**，在用户客户端本地执行；不是用户自己维护运行参数的功能。
2. 脚本是独立资源，拥有独立版本、审核及发布机制，可以被 ApplicationVersion 引用；不是嵌入 ApplicationVersion 的可变代码字段。
3. 当前内容是 JSON，后续可能使用 Lua。服务端先按纯文本管理，不过度解析其内部结构。
4. 脚本目前采用与 ApplicationVersion 相同思路的人工审核机制；后续可以加入机器检查。本轮不实现机器检查执行器。
5. ApplicationVersion 填写使用的脚本版本时，可以选择正在审核、尚未获批的版本，不能要求脚本先获批才允许应用准备和提交审核。
6. 审核先完成脚本，再完成依赖它的 ApplicationVersion；应用审核结果受脚本审核结果约束。前端支持串联操作，后端必须维护真实依赖和一致性，不能只依靠页面按钮或操作顺序。
7. 用户已选择：**脚本版本被拒绝后，自动拒绝所有引用它的待审 ApplicationVersion**，不是仅提示阻塞后等待人工拒绝。
8. 用户已确认：脚本管理正式放进 **App Center 服务内部**；采用同服务、同数据库的独立脚本领域，独立资源、版本、API、审核和发布机制继续保留，不新建 Resource Hub 服务。

下文的精确版本绑定、提交栅栏、级联事件及分批处理是实现这些目标的建议方案，尚待用户审核。

## 服务和资源边界

脚本管理正式属于 App Center：App Center 拥有脚本内容/版本、审核事实、独立发布历史以及应用审核依赖。脚本与 ApplicationVersion 保持独立业务身份，按精确版本关联；客户端仍负责本地执行、凭据及运行隔离。

此前 [产品范围](../product-scope.md#平台爬虫配置管理2026-11-05-新增范围)中的通用 Resource Hub 排除项不再排除此平台脚本能力。新增范围和服务归属已经确认，具体状态迁移与不变量现由待审 UC041–049 定义；不把范围确认说成后端已实现。

原初稿的“第三方 Developer 上传、以后才关联应用、任意 bundle 制品平台”不再作为当前方案。首期围绕平台维护的单份文本配置及与应用审核的必要关系展开；不加入共享 KV、通用配置中心、服务端爬虫执行、云端代登录、采集结果上传或新客户端目录实现。

平台维护人与脚本 Reviewer 的精确资格、权限及利益冲突规则需要在正式 UC 中确认；“平台维护”不自动等于所有完整平台管理员均可编辑或审核，也不自动复用 App Reviewer 的权限。客户端 Runner、安全执行与本地凭据由客户端所有者设计，本文不代替该交付。

## 建议对象模型

| 对象 | 建议职责 |
| --- | --- |
| ScriptResource | 稳定脚本 ID、名称、用途及资源可分发状态，平台维护；不以 applicationId 充当身份 |
| ScriptVersion | 独立不可变版本 ID、版本标签、contentFormat、精确文本/内容引用、digest、审核状态与 revision |
| ScriptReview | 针对固定 ScriptVersion 内容的审核提交、绑定政策及一次性批准/拒绝事实 |
| ScriptPublication | 独立发布选择、revision 和历史；具体渠道、历史版本保留的分发资格待审 |
| ApplicationReview 的脚本引用快照 | 被本次应用提交固定引用的 ScriptResource/ScriptVersion 及内容摘要，不保存一个随 latest 改变的引用 |
| 审核依赖关系 | 反向定位引用精确 ScriptVersion 的待审 ApplicationReview，支持拒绝级联与可追溯原因 |

ScriptVersion 一旦提交审核，其文本、格式及受审声明冻结；修正内容使用新版本/新 ID，不能在同一个待审或已审核版本上换字节。App 自身仍沿现行 DRAFT 修改与 revision/OCC 规则；更改脚本引用属于应用受审核内容变化。

### 纯文本与 JSON/Lua

首版建议受理有界 UTF-8 文本及显式 `contentFormat=json`，保存/返回所受理文本的精确字节及摘要。不得自动 JSON 格式化、重排键、改写换行，或把 JSON 内部字段拆成服务端的业务真相。大小、空文本、编码和摘要等输入边界在正式 UC 中冻结；它们不等同于脚本逻辑审核。

首期不依赖 JSON 内部 Schema、AST、执行结果或自动能力推断。所需人工检查及必要外部说明由正式审核政策定义；不因文本看起来像合法 JSON 就判定可执行或审核通过。

以后增加 Lua 时，通过新版本的显式格式和对应 Runner 支持交付；不靠扩展名/内容猜测，也不在原版本内把 JSON 改成 Lua。不为尚未上线的旧数据或旧客户端增加格式转换、双读或迁移兼容分支。JSON/Lua 内容管理与客户端实际执行协议分开定义。

首期只需受限的文本保存、版本读取与内容获取语义，不预建任意文件上传、解压、依赖下载或通用制品平台。文本是否另存对象存储属于后续实现选择，不影响审核字节必须与分发字节一致的规则。

## 独立审核与未来机器检查

当前建议采用与 App 一致的基本思路：不可变提交快照、提交时绑定正式政策、Reviewer 明确确认人工检查项、一次性决定及审计。政策 ID、正式文本与权限由正式 UC 定义，不复制 App v3 的检查 ID 作为脚本政策，也不因 App Reviewer 身份自动获得脚本审核权。

脚本审核与应用审核是两个独立命令。即使同一人具备两项资格，也必须分别鉴权、分别留下决定，不能用“批准应用”暗中批准尚未获批的脚本。用户所说的前端先后操作由页面编排，不把它变成后端批量绕过。

未来机器检查必须针对相同 ScriptVersion/digest，保留检查器/规则版本及结果，且不能修改被检查文本。本轮只保留这种扩展边界，不提前建立检查任务状态机、自动执行上传脚本或合成“机器已通过”结果。机器结果何时参与最终批准、错误与拒绝如何区分，后续另行接受；不能事后默默改写既有人工决定。

## ApplicationVersion 的精确引用与审核顺序

### 填写、修改与送审

建议引用以精确 ScriptVersion ID 为目标，并验证它属于给定 ScriptResource；不只绑定资源 ID 或移动的 latest 发布指针。App 提交时将引用列表和摘要一起固定进 ApplicationReview.snapshot，脚本引用也参与 source revision 和内容一致性核对。

- 正在审核的脚本版本可以被选择，也可以与引用它的应用一起处于待审状态。
- 已批准脚本可以被引用。不存在、归属不符或已拒绝的脚本不能产生新的成功应用送审；原已选择该脚本的应用草稿可保留并显示需要修改，不凭空为 DRAFT 创建拒绝审核记录。
- 可选择的候选需要最小版本元数据与审核状态读取；可选择不等于可执行或可以提前把未获批正文分发给普通客户端。具体候选可见性、Reviewer 内容读取和权限由 UC 明确。
- 引用数量上界、重复项和同一资源引用多个版本的规则，正式 UC 中另行冻结；不能静默以最后一个引用覆盖前面的引用。

### 应用批准的强制前置

**ApplicationReview 只有在全部精确依赖脚本版本已获批后，才能批准。** 这是后端条件，不是一个可由客户端传 true 的确认框。未引用脚本的应用仍须经过现行全部 App 审核门禁。

前端可展示依赖状态并跳转先审脚本，完成后明确刷新应用详情，再提交应用批准；不自动重放旧批准请求。后端直接调用、迟到请求、缓存结果或不同 Reviewer 并发都不能绕过依赖。

后端在最终决定边界确认引用仍等于该 App 快照，并核对可验证、已提交的脚本批准事实；不得只相信页面送来的状态或服务端先前缓存的 pending/approved。批准记录应能追溯所依据的 ScriptVersion/digest/脚本审核决定。缺依赖、数据不一致、依赖不可读不能当作已批准。

ScriptVersion 的拒绝和批准为相斥的一次性结果，已提交文本不可变。一个脚本批准事实不能后来在原 Review 上改成拒绝；暂停、撤销资格或未来复审属于单独治理设计，不和本轮初次审核结果混用。

## 脚本拒绝后的自动级联

用户已确认级联目标为：**引用该精确脚本版本、仍处于待审状态的全部应用审核**。不是拒绝同一 ScriptResource 的所有版本，也不改写已决定的应用历史。

### 建议可靠处理方案（待审核）

1. 脚本的拒绝决定与持久化级联事件/处理任务同事务提交。事件固定 scriptVersionId、digest、脚本 review/decision ID、原拒绝事实与触发人，不依赖一次临时 HTTP 通知。
2. 后端按反向依赖关系有界枚举仍待审的应用审核。每条自动拒绝在 App 的原子决定边界同时更新 Review、Version/revision 与相应审计；保留原 App snapshot 和政策绑定。
3. 自动决定由明确的 SYSTEM 来源执行，记录“因引用脚本版本被拒绝”的因果及原脚本决定；不冒充持有 app.version.review 的人工 Reviewer，不向普通用户开放伪造级联事件的入口。具体 System 身份/内部调用权限按现有权威契约扩展审查。
4. 处理幂等，以原脚本拒绝事实及目标 App reviewId 定位。重试、重复投递、响应丢失不能增加第二次决定或审计。若 App 已被人工拒绝、其它依赖级联或现行资格规则决定，则保留原终态，不能覆盖其原因。
5. 进程重启或部分任务失败后继续扫描/重试，保留可核对进度与完成条件；不能发完事件就声称所有关联审核均已处理。
6. 无论级联是否已完成，应用批准路径都核对脚本依赖；脚本已拒绝时必须拒绝批准请求。前端可显示“依赖脚本已拒绝，应用审核自动拒绝处理中”，不能把仍待处理的物理 PENDING 当作可批准。

这是建议的“安全前置立即成立，所有待审对象可靠收敛”的方案，**尚未承诺脚本拒绝 ACK 与任意数量应用的终态在同一瞬间完成**。同步全部拒绝还是持久化分批级联，以及 UI 的处理中观察，需要用户审核；不能用一个无界大事务来假装问题已经解决。

### 送审与脚本拒绝的竞争

必须防止“脚本拒绝后级联扫描已完成，但一个稍后提交的应用又引用它变成待审”。应用成功送审、依赖登记与脚本终态转换需要明确的后端串行关系。

同库事务方案可以让应用送审在引用脚本的权威状态文档上作真实条件写，并在同一事务登记冻结依赖：

- 应用送审先提交：待审 Review 和依赖已经保存，随后脚本拒绝一定产生覆盖它的级联义务。
- 脚本拒绝先提交：应用送审重试后看到 REJECTED，不能再新建引用它的待审 Review。
- 应用送审或依赖登记失败：两者一起回滚，不产生缺反向依赖的待审审核。

应用最终批准同样必须核对已提交批准事实；脚本待审/已拒绝时都不能抢先批准。App 的手工拒绝、资格自动拒绝和脚本级联相互竞争时，仍遵守同一 Review 只有一次终态。

本轮使用 App Center 同库事务建立这些串行关系，不再把跨服务登记/拒绝传播列为当前方案。级联任务仍须持久化、幂等并可恢复，同服务不表示可以用临时内存通知或无界大事务替代可靠处理。

## 独立发布与执行时使用哪个版本

脚本获批与脚本发布分开，不能把脚本获批理解为自动推给所有客户端。**建议 App 审核依赖脚本批准事实，而实际发布/执行另核对所引用版本的分发资格**；这一区分还需在发布 UC 中接受。

App 绑定 A，不会因为脚本独立发布了 B 就改用 B，也不跟随 latest 自动更新。更改应用引用需要应用的新受审内容；否则脚本可以绕过 ApplicationVersion 的已审核依赖。

是否保留仍可分发的历史脚本版本、具体渠道和回退语义待审；若选择保留，发布 B 不应仅因 head 移动就让 App 对 A 的精确引用失效。暂停/撤销分发时的 App 发布和客户端执行门禁也需明确，不凭人工审核历史永久授权分发。

客户端取得确切 versionId、contentFormat、digest 和原文/受控获取方式，并按自己的 Runner 能力执行。不允许解析器悄悄用另一个脚本版本替换不兼容或不可用依赖。停止分发不能收回已下载字节或承诺立即停掉本地执行；离线与已缓存内容边界由客户端契约确认。

## 已确认的服务归属与待决策

2026-11-05 用户确认将脚本能力正式纳入 App Center。服务内保持独立领域、资源 ID、版本、审核和发布 API；脚本决定、App 送审依赖登记以及级联义务由 App Center 在同库事务边界内协调。脚本业务版本独立发布，后端仍随 App Center 服务交付。

不新增独立 Resource Hub 进程、数据库、服务 audience 或跨服务提交协议。Auth 后续只需为被接受的脚本精确权限确认现有 App audience 投影；权限名称与授予规则仍待设计，不自动把现有 App Reviewer 或平台管理员变成脚本维护/审核人员。

未来机器检查可按需要由后台 worker 执行，脚本和审核依赖的权威事实仍归 App Center；本轮不实现该 worker。若以后确需拆服务，应另行接受架构变更，不能把它保留为当前并行路线。

仍待冻结的内容：

- 平台维护、脚本审核、发布和暂停的精确权限及利益冲突；不再以第三方 Developer 上传为首期前提。
- 脚本独立发布的首版渠道、历史版本分发资格，以及 App 发布/运行如何核对精确依赖。
- 可靠分批级联与 ACK/处理进度语义，或有界同步方案；同库事务的精确条件写、依赖索引和级联完成判据。
- 客户端对 JSON 及未来 Lua 的 Runner 协议和本地权限/凭据边界；服务端继续保持文本管理。

## 候选用例与验收设计

服务归属已经确认；2026-11-05 用户要求开始用例设计后，已分配 UC041–049、BR-SCR/SDP 和 ADR008，全部待审。下表保留最初工作包划分，当前正式拆分及串行顺序以[用例审核清单](2026-11-05-crawler-script-use-case-review.md)为准；接受后才修订现行 App 审核用例与相应 brief。

| 工作包 | 必须覆盖 |
| --- | --- |
| 平台创建脚本与文本草稿 | 独立 ID、权限、格式、文本上界、digest、revision/OCC |
| 提交、查询与决定脚本审核 | 冻结内容、提交绑定政策、人工检查、一次性决定、拒绝事件的原子落盘 |
| 独立发布、查询历史、暂停与恢复分发 | 获批不等于发布、精确历史版本、发布前置与审计 |
| App 创建/编辑脚本引用并提交审核 | 接受 pending 引用、冻结引用与摘要、反向依赖登记、送审/拒绝两种胜序 |
| App 审核详情和批准/自动拒绝 | 展示依赖、批准前置、可靠级联、SYSTEM 因果、幂等与终态竞争 |
| App 发布及客户端内容解析 | 使用受审精确版本、分发资格、digest/格式校验、不跟随 latest |

有界验收至少覆盖：pending 脚本和应用可先后送审；待审脚本阻止应用批准；脚本获批后应用可正常人工审核；脚本拒绝自动拒绝所有精确引用的待审应用；多依赖任一拒绝、重复投递/重启/部分失败恢复；App 送审和脚本拒绝两个提交胜序；与人工拒绝/资格自动拒绝竞争不覆盖终态；未依赖该版本的其它 App 不受影响；内容/格式变化创建新版本；JSON 不被深度解析或自动改写；客户端取得审核时同一精确文本；发布 B 不静默替换应用绑定的 A。

本轮新增 App 侧待审 UC/BR/ADR 与注册表索引，未修改既有已接受 UC、API 或业务代码，尚未执行新业务测试。Auth/Gateway/Console 的权威 UC、API 和代码未触碰；Auth agent 当前独立本人运维权限读取工作保持原样。

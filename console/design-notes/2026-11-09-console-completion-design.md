## 建议的页面责任

平台脚本由 Admin Console 维护，Developer Console 只在应用版本中选择依赖。建议将 Developer 现有全局“爬虫配置”占位入口移至 Admin 的“脚本配置”，不让应用管理员误以为自己必须维护平台脚本。如果将来增加真正属于 Developer 的爬虫任务或站点配置，另立能力与 UC，不在此次借用平台脚本资源模型。

| 入口 | 页面作用 | 权威 UC |
| --- | --- | --- |
| Admin → 脚本配置 | 资源列表、资源详情与元数据、版本列表 | [UC019](../use-cases/UC-CONSOLE-019-script-resource-workspace.md) |
| 资源 → 版本工作页 | 新建与编辑复用全页；已送审版本只读；拒绝后建立新版本 | UC019 |
| Admin → 审核 → 脚本审核 | 与应用版本、公开资料平级的独立待审队列及详情 | [UC020](../use-cases/UC-CONSOLE-020-review-script-versions.md) |
| 资源 → 发布与分发 | 当前推荐版本、发布历史、资源暂停/恢复 | [UC021](../use-cases/UC-CONSOLE-021-script-publication-and-distribution.md) |
| Developer → 应用 → 版本工作页 | 选择精确脚本版本、展示依赖就绪情况 | [UC022](../use-cases/UC-CONSOLE-022-application-script-dependencies.md) |
| Admin → 应用版本审核详情 | 固定脚本引用、受限原文及应用批准阻塞原因 | UC022；沿用原应用审核工作页 |

资源详情中的版本、发布与分发、资源资料是平级分区。版本编辑、脚本审核和关联原文读取可以有独立 URL，但不是必须依次经过的多层向导；返回时恢复来源列表的合法筛选和分页。页面职责与导航关系已随上述 UC 接受，具体布局与视觉实现后续迭代。

## UC015 已接受增量：脚本五权限治理

已接受方案复用现有人员精确定位和按目标读取/逐项授撤结构，在人员治理增加“脚本权限”分区，不新建一套人员目录。业务权威为 [Auth UC038](../../auth-center/use-cases/UC-AUTH-038-manage-script-maintainer-permission.md)。

五个动作分别为维护、审核、发布、暂停分发、恢复分发，显示其独立授予与生效状态。选择目标后使用正式五权限 Get，单次确认只提交一个权限动作，并使用该次目标读取的共享 permissionRevision。任一已观察到的同目标更高权限修订使旧确认失效。管理入口仍要求完整平台管理资格；拥有某项脚本执行权不等于可以给他人授权。

授予条件、停用目标的可操作范围、原因限制与有效期边界只引用 Auth，不在 Console 另建规则。失败、无授予、暂不生效分别表达；不因授予一项自动勾选其他项。沿用 UC015 的会话隔离、未知结果只读核对与专用范围退场。增量已合入 [UC015 正文](../use-cases/UC-CONSOLE-015-manage-platform-governance.md)，本节仅作导航。

**外部依赖 AUTH-D1（设计与后端已交付）**：用户于 2026-11-10 明确批准 [Auth UC038](../../auth-center/use-cases/UC-AUTH-038-manage-script-maintainer-permission.md) 的本人读取，Auth/API 和 Gateway 精确路由已实现。Console 使用正式 GET 读取本人五项完整状态，不调用管理员目标 Get 探权。固定 API 241d56d、Auth 本地源码指纹及镜像、Gateway 78d74f7 的来源和联合验收记录见[本轮实施记录](../implements/2026-11-10-script-and-management-activity.md)。

## 已接受的共享前端行为

下述内容概述 UC019–022 的共同实现输入；完整语义以对应正文为准：

- 复用既有组件、TanStack Query、Session 绑定私有请求与同源 Gateway 流程；原生 fetch 封装使用官方生成类型，业务服务不经过特权 BFF 代行授权。新本人发现契约未定稿前不发明临时 DTO。
- 列表只消费正式分页，每页建议20项；筛选/身份变化重建分页链，不虚构总数，不后台穷举。正文按详情需要加载，不放入列表或全局预取。
- 大量编辑使用全页；小型确认可用对话框。revision/digest 等技术信息用于并发与详情核对，普通操作不显示“使用 revision N”或要求手填修订。
- 创建由用户明确触发。已有草稿可串行自动保存，保存状态区分待保存、保存中、已保存、失败及结果待核实；送审、发布、暂停等命令必须明确确认，禁止自动重放。
- 会话变化、目标变化、权限明确失效、离页后，旧成功和旧拒绝都不能更新新页面或触发写入。内容、审核原因、权限状态只在当前私有内存；不进入 URL、localStorage、通用遥测或测试附件。
- 冲突不覆盖服务器；写入结果未知先只读核对。当前状态吻合不证明原请求一定成功；恢复后如需再次写入，应从新基线重新确认。正常网络重试不能变为命令重放。
- 内容作为文本展示，不执行、不注入 HTML；下载或编辑转换不得悄悄改变后端审核的字节。可访问名称、键盘入口、焦点恢复、保存与错误状态提示随页面交付。

## 已实现功能的联合验收工作包

这两项属于验收补齐，不新建重复业务 UC，不在本轮设计期间运行完整测试。

### V1：正式审核策略 A→B

依据 [UC006](../use-cases/UC-CONSOLE-006-review-application-versions.md)、[UC007](../use-cases/UC-CONSOLE-007-review-application-profiles.md) 与[当前实施边界](../implements/2026-11-04-submission-bound-review-policy.md)。App owner 需先确认正式发布/恢复路径、候选 B 的实际业务差异和环境；用户批准候选后才切换，不自行制定生产审核政策。

对 Version 与 Profile 分别记录：在 A 下提交并打开待审详情 → 正式发布 B → 旧待审仍按绑定 A 呈现与决定、新提交绑定 B → 历史保持原事实。已勾确认能否保留由绑定快照、完整定义及现有确认身份是否相同决定；仅服务当前策略切换不应重绑旧提交。Scope、权限、快照或相关前置事实变化仍依既有规则重新确认。

补验发布回执丢失后依原 releaseId、原子回执/发布账本与运维读回恢复；操作接口若限内部，不在 Console 增加策略管理页。不得直接改 DB 冒充正式发布、仅替换 fixture 冒充真实切换，或把旧政策退休误判为待审失效。需保存镜像身份、API/Console 提交、实际发布记录、两类审核读回及终态证据。

**外部依赖 APP-D2**：请 App agent 核对已有设计；缺少时给出待审验收安排与候选策略差异。仅缺部署环境属于执行依赖，不重复创造后端业务设计。

App 已提交[策略候选与联合验收草案](../../app-center/design-notes/2026-11-09-review-policy-release-joint-acceptance-proposal.md)。核查确认原子发布/恢复已有权威与内部原语，仍需专用发布包接入正式迁移入口、确保重复执行仍核对原清单，并补最小运维读回。候选 V 为 Version v4 新增“脚本用途与应用声明”人工核对，候选 P 为 Profile v2 新增“主体与认证表述”人工核对；两者会增加实际审核义务，均未获批准。用户可选其中一类、两类、修改或暂缓，不为关闭测试证据自动采用新政策。建议独立本地验收栈、逐类执行；现有环境切换不在本轮设计授权中。

### V2：非平台管理员真实运维组合

以真实 Auth 授撤、Console Cookie/Gateway 链和真实 App 状态读取为依据，补齐下表；后端单测、前端 fixture 与完整管理员代表链不替代本表。

| 当前人的实际 grant | 预期入口与动作 |
| --- | --- |
| 无 search/suspend/restore | 不显示目录或运维写入 |
| suspend-only | 已知 ID 专用读取与暂停，无目录或恢复 |
| restore-only | 已知 ID 专用读取与恢复，无目录或暂停 |
| suspend + restore | 已知 ID 读及两个独立动作，无目录 |
| search-only | 目录与最小摘要，无运维写入 |
| search + 单项动作 | 目录定位后只执行已授权动作 |
| 完整平台管理员 / Reviewer / owner，但无上述 grant | 不从身份隐式扩张目录或运维权限 |

每种代表组合补验当前会话正式授予/撤销后的重新发现、账号失效、迟到响应、独立403、旧确认失效与一次写入结果未知。明确权限撤销只关闭相应范围，不关闭无关审核或人员治理。测试账号由正式后端流程建立，不能写数据库或在 BrowserSession 塞 permissions。

## 审核点与建议顺序

本轮前端已接受：平台脚本入口放在 Admin，Developer 只选择应用依赖；新建/编辑复用全页并在初次创建后自动保存；脚本审核独立队列；单一推荐版本与资源级分发门禁；五权限治理并入现有人员页。

建议顺序为：UC019与权限发现/治理 → UC020 → UC021 → UC022 → 真实脚本/应用联合链。V1/V2 的环境与角色准备可独立进行。每个实现工作包按必要检查验证，不对每次视觉修改重复跑全套测试；只有真实链证据完成后才在 implements 标记其覆盖范围。

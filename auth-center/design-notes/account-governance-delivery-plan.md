# 账号与平台资格治理设计草案

状态：`PROPOSED`

日期：2026-10-05

本文规划后续 UC 的边界、顺序和接受条件，不修改已接受 UC 的权限或状态契约，也不表示下列能力已经实现。管理员管理已分配 UC021 并在 design-registry 登记；其余候选尚不预占编号，本轮不生成实现 brief。已有同账号 Session 管理继续由 [UC020](../use-cases/UC-AUTH-020-manage-own-sessions.md) 跟踪。

## 建议拆分与顺序

| 顺序 | 候选用例 | 操作人 | 主要结果 |
| --- | --- | --- | --- |
| 1 | [UC021：授予与撤销平台管理员资格](../use-cases/UC-AUTH-021-manage-platform-administrators.md) | 有管理管理员资格的管理员 | 后续管理员能够被正式授予和撤销；防止失去最后一个有效管理员 |
| 2 | 禁用与恢复用户账号 | 有账号治理权限的管理员 | 暂停整个账号的使用资格；恢复后重新登录 |
| 3 | 暂停与恢复 Developer 资格 | 有 Developer 治理权限的管理员 | 限制开发者活动，保留普通用户身份及应用归属 |
| 4 | 退出 Developer 资格 | 本人 | 处理完名下应用后退出资格，保留普通账号 |
| 5 | 注销本人账号 | 本人 | 完成资格及应用归属清理后，终止账号并清理其个人数据 |

禁用后的恢复与注销后的撤回是不同问题，分别设计。Developer 行政暂停和本人主动退出也分别设计，避免复用一个状态却产生不同恢复权限。

上线前建议交付管理员治理、账号禁用/恢复，以及可执行的本人注销路径。开放 Developer 平台前再满足 Developer 暂停/恢复、退出和 App 应用处置的联动条件。注销可以先覆盖没有应用归属的普通用户，但必须明确告知其适用范围；不能把尚无处置流程的 Developer 注销入口宣称为可用。

## 一、授予与撤销平台管理员资格

已展开为 [UC021](../use-cases/UC-AUTH-021-manage-platform-administrators.md)，状态 PROPOSED。固定权限集合、在线授权、最后管理员保护、共享版本、首次初始化和旧部署显式迁移以该 UC 的 BR-ADM-001–008 为草案规则来源；本计划不重复定义。UC004 继续只管理应用审核权限，既有接受契约需在 UC021 接受时同步调整。

## 二、禁用与恢复账号

建议沿用 `ACTIVE → DISABLED → ACTIVE`，仅管理员执行；用户不能通过注册、邮箱登录或重新提交设备证明恢复原账号。

禁用针对整个 authId：阻止新登录、Session 使用、可信身份签发，以及该用户作为授权人的 OAuth 使用。建议使既有 Session、OAuth token family 和待完成的认证/授权操作永久失效；恢复只恢复账号使用资格，必须重新登录、重新取得应用访问凭据，不能让旧 token 因状态恢复而复活。历史 consent 可保留，恢复后是否需要补充同意仍按 UC014 判断。

设备公钥和邮箱绑定可以保留供恢复后重新认证，资料和应用归属也不因禁用被删除。资格和独立权限的撤销仍是独立操作；管理员恢复账号不重新授予已撤销权限，也不解除 Developer 暂停。

正式 UC 必须决定并验证如何使禁用前的 Session、邮箱 challenge、设备 challenge、授权请求及授权码在恢复后仍不可使用。可以采用生命周期版本栅栏或显式撤销，但不能只有一处 accountStatus 写入。所有认证完成路径都要纳入并发验证。

已有离线验签的 USER/委托 JWS 不能被 Auth 瞬间收回，其残余有效期由既有 TTL/leeway 决定。若消费方需要更快阻断，则需要另行增加在线状态检查契约，不能承诺禁用提交后所有在途请求立即消失。

## 三、暂停与恢复 Developer

建议只允许管理侧 `APPROVED ↔ SUSPENDED`，填写原因、使用资格版本并写独立生命周期审计。普通用户 Session、邮箱登录和资料访问继续可用；审核权限、管理员权限不因 Developer 暂停而隐式改变。

恢复保留原 developerHandle 和应用归属，不创建新的 Developer 身份。暂停不是删除应用，也不是清除审核与发布历史。

当前 OAuth 会检查应用所有者账号可用且 Developer 为 APPROVED，因此暂停所有者能够阻止相关 OAuth 在线使用；这不代表应用从公开目录或统一启动入口消失。暂停前的短期 Developer JWS 也需要消费方明确失效窗口，不能只在 Auth 增加写接口就宣称所有开发操作即时禁止。

建议 Developer 暂停表达“暂时不允许继续行使开发者资格”，App 的“应用紧急停用”表达“应用不能继续对外服务”，两项操作分别审计、明确组合。是否自动联动由跨服务用例决定；Auth 不直接写 App 数据库。

当前所有者资格恢复后，仍在期限内且未被撤销的应用用户 OAuth 凭据可能重新可用。建议保留这种临时资格检查语义；若处理的是应用安全事件，应另外执行应用停用或 client/token 撤销，不能把临时 Developer 暂停当成永久撤销所有应用用户授权。

## 四、退出 Developer

建议本人主动退出仅适用于 APPROVED Developer；SUSPENDED 不允许通过“退出再申请”绕过治理。退出保留普通 USER、本人登录和资料。

建议引入明确的 `WITHDRAWN` 状态，而不是回到 null 或复用 SUSPENDED；这是待接受的契约扩展。developerHandle 的永久占用继续遵守 [UC013](../use-cases/UC-AUTH-013-apply-for-developer.md)，不因退出而释放。将来重新开通也只能沿用原 handle；是否首版允许重新开通，需在本用例与 UC013 一起决定。

退出前必须由 App 确认没有需要该账号负责的应用归属或进行中的所有权变更。仅仅没有已发布应用不够，草稿、审核中应用也需要处置。应用应先转移或按 App 定义关闭，再退出资格。

这一前置检查不能采用“查一次没有应用，然后修改 Auth 状态”的无保护流程：并发创建应用可能穿过检查。正式跨服务契约必须覆盖冻结新的开发操作、处置/确认归属、最终退出以及失败重试，不能依赖跨库事务或人工直接改库。

接受条件包括更新 [UC002](../use-cases/UC-AUTH-002-batch-get-developer-statuses.md)、UC013、可信身份状态校验及所有 App 消费方。当前 UC002 的枚举和部分 App 暂停检查并不自动支持 WITHDRAWN；不能只增加 Auth 枚举。

## 五、注销本人账号

建议作为独立的明确确认操作，作用于当前认证的 authId，绝不扩大到同一 associationId 下的其他账号。注销不是退出登录，也不是管理员可以恢复的账号禁用。

建议首版采用无自动恢复窗口的注销方案，以减少“已经删除但又能恢复”的语义和存储复杂性；这是草案建议，正式接受前需要确认。提交前展示清理范围并要求近期重新认证；设备凭据账号可用新的设备签名证明，不能强制所有普通用户先绑定邮箱才能注销。具体挑战、时效及一次性消费规则由正式 UC 固定。

建议前置条件：不得是最后一个有效管理员；持有管理资格者先完成交接并撤销自身管理资格；Developer 先完成应用处置并退出。禁用账号如何通过独立身份核验申请注销，需要另行规定受理流程，不能因普通 Session 不可用而永久没有注销途径。

注销分为逻辑终止和数据清理：终止一经确认，账号永久不能登录，Session、认证挑战、OAuth code/token family 永久失效；后续清理必须幂等、可重试且不能把失败解释为账号已恢复。物理清理完成前不向用户声称所有数据已删除。

正式 UC 接受前需要逐项确定：

- 用户资料、邮箱绑定、设备公钥、Session、grant、token、pairwise 映射及账号到 association 的关系各如何清理。
- 邮箱何时允许重新注册；新注册必须创建新 authId，不能接回旧账号或旧授权。
- 仍被其他账号使用的学生关联组不能随本账号注销被删除；关联组本身的保留期另行确定。
- developerHandle 永久占用、必要主体墓碑和审计如何最小化保留，分别有何期限与用途；不得把“保留审计”解释为永久保存全部资料。
- App 中应用、审核记录等历史主体引用，以及备份、日志和第三方已取得数据的处理边界。Auth 注销不能宣称已经删除第三方数据。

## 交付门禁

优先评审已展开的 UC021，随后设计账号禁用/恢复；两者建立后续治理的操作权限和最后管理员保护基础。Developer 暂停/恢复可以继续复用现有枚举，但仍需 App 逐入口确认生效范围。

Developer 退出和账号注销应同步设计，但在 App 提供归属处置与并发协调契约、Auth 明确终止及数据保留策略之前，不生成标为可实施的 brief。这些依赖不阻止先完善普通用户治理或同账号 Session 管理。

# 邮箱账号、校园认证与应用次数权益参考

状态：`GUIDANCE`

2026-10-12 产品方向已确认。账号规则以 UC006/011/012 为权威，校园认证以待审核 UC031 为准；本文仅给开发者提供相对可靠的次数方案参考，不定义 Auth 业务规则或待实现权益工作包，不决定数量、发放和扣减。

## 已确认的账号方向

平台注册明确发起、验证邮箱并设置平台密码；邮箱列表中恰好一个登录/恢复角色，切换需密码，当前登录邮箱验证码可重置密码。修订 UC006/011 尚未实施；无邮箱创建仍退役，登录失败不自动注册，角色切换不改变 authId。

取消注册上传学号、学号散列、associationToken 及其它学校关联声明；不再创建学号关联组，也不把客户端学校信息作为账号或权益归属依据。一卡通号是已接受的可选资料字段，与学号关联声明不同，不在本次顺带删除。

设备公私钥首版保留为后台记住登录和高风险操作证明；它是 App 自管设备凭据，不称作标准 WebAuthn Passkey。用户通过邮箱恢复原账号；不再把保有本机私钥作为唯一恢复路径。

校园认证引用修订 UC031：当前有真实验证的精确 `whut.edu.cn` 绑定则认证，无周期复验；解绑最后依据撤回，重新绑定可恢复。不因自填资料或未验证后缀授予，也不证明在校学籍；旧永久事实实现不能当作新绑定模型已交付。

## 权益的所有权

次数、余额、赠送数量、扣减与退款均属于提供该权益的应用。Auth 只持有账号、认证与 OAuth 授权，不建设平台通用权益钱包，也不为第三方直接修改次数。

业务主体是稳定的 iWUT 账号。第三方按自己 Application 范围内的 `(issuer, pairwise sub)` 识别账号；同 Application 的 client、major 和 Version 共享 sub。原始 authId、学校邮箱或客户端学号不能作为终端指定的消费主体。

校园认证可以成为应用的一次性赠送条件。应用使用受信的认证事实自行决定是否发放；认证并不自动产生权益，也不承诺跨应用共用次数。

无需周期复验不等于解绑后仍认证；应用赠送仍按账号/活动一次，解绑/重新绑定/恢复认证不重置领取记录，也不由 Auth 自动回收余额。首版不承诺每自然人或每校园邮箱只能领一次：注销新账号可能再次符合条件；业务跨账号防重复须独立设计，不增加 Auth 永久邮箱消费库。

## 给开发者的次数权益参考

一次性赠送记录的业务唯一键为 `(application, ledgerNamespace, issuer, sub, benefitCode)`。ledgerNamespace 由应用服务端把已验证 channel 映射为账本空间，不能取客户端自报 environment；benefitCode 是应用维护的稳定权益活动标识。重复登录、重复认证、OAuth 撤权后重授权、邮箱更换、client/Version/major 变化都不重建这条记录。

TEST、GREY、STABLE 的消费凭据保持当前渠道校验；测试账本必须与生产账本隔离。GREY 与 STABLE 是否共用生产余额由具体应用明确配置，不能由客户端改选；若共享，领取记录与余额都映射到同一个生产 ledgerNamespace，不能只共享余额而重复领取。

领取时在应用一次事务中复核未领取、写入唯一领取记录，并把固定的活动数量增加到该账号余额。双击或并发领取最多成功一份；网络结果未知时读取领取状态，不用新请求反复发放。活动数量未确定前不实现真实发放。

消费使用应用固定功能、明确的正整数消耗量和稳定 requestId。应用服务端确认当前可信主体，原子地检查余额、扣减并建立业务操作记录；相同 requestId 和相同输入重试返回既有结果，不再次扣减；相同 ID 不同输入拒绝。

应用服务端保存三个独立记录：

| 记录 | 作用 | 关键约束 |
| --- | --- | --- |
| GrantReceipt | 某账号领取某活动的事实及当时发放数量 | 活动领取唯一键；活动改数量不重发旧领取 |
| CountBalance | 某账号某种次数权益的余额 | 区分权益种类与赠送活动；余额与流水同事务更新，不能小于零 |
| UsageOperation | 一次业务执行的占用、成功或退回记录 | 账号范围内 requestId 唯一、输入摘要固定、终态不可重复扣减或释放 |

不同活动可以增加同一种权益余额；活动配置规定赠送到哪一种权益，不能把活动 ID 当作唯一钱包种类。客户端只提交业务输入和 requestId，不能决定发放数量、扣减量、余额或退款结果。

若业务结果也能在同一数据库事务中提交，业务结果、扣减与记录一并提交。若依赖外部执行，则按 `RESERVED → SUCCEEDED / RELEASED` 管理：先占用额度，再执行外部业务，明确失败只释放一次；超时或未知结果保持待确认，后台查询后收敛。不能因客户端报告失败就退款，也不能在数据库事务重试中执行外部动作。

外部执行还要求业务自身支持幂等执行键或可查询结果；如果两者均没有，未知结果无法安全地自动重做或退款，必须先解决这个依赖。首版消费前余额表示可用次数，RESERVED 已扣除可用次数；SUCCEEDED 不再扣一次，RELEASED 按原占用量只加回一次。

ApplicationUserStorage（UC030）是应用用户 KV，不是次数账本。持有 `storage.write` 的客户端可以修改 KV；应用的领取、余额、流水必须由应用服务端独占维护，不能信任客户端可写存储中的次数。App Center 管理的是应用发布与运行资格，不因某个官方应用提供次数权益就成为它的钱包服务。

首版仅一次性赠送、非负整数余额、明确扣减和幂等退回；周期重置、过期、付费购买、转让、跨应用钱包、账号合并均另行设计。具体应用若需要这些能力，应先修订其权威用例。

## 参考方案的适用边界

1. UC031 旧独立永久事实基线曾 ACCEPTED/后端通过；本次当前绑定/撤回修订为 DRAFT，尚未实施。应用须消费可信且当前有效的授权事实，不能借 profile 或未验证邮箱后缀推断认证。
2. 学校邮箱别名无法由 Auth 可靠归并；首版按账号领取，不做跨账号、跨应用自然人归并。活动是否接受注销新账号再次符合条件，需要具体应用确认。
3. 开发者自行决定权益种类、benefitCode、数量、消费业务、失败判定和渠道账本隔离；这些不是 Auth 实施前提。本文不创建应用、不提供 SDK/钱包服务、不发放额度。

此前邮箱 v2/关联退役与永久认证基线已实现，后台登录保留；新增密码、邮箱列表和当前认证依据修订仍 DRAFT，须依赖闭合、用户审核后 ACCEPTED，再生成开工 brief/实施。应用自己的次数规则不阻塞 Auth，历史验证见 implements。

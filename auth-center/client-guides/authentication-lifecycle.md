# 客户端认证生命周期建议

状态：`GUIDANCE`

本文给官方客户端提供注册、登录、账号切换和退出的推荐编排，不是 Auth Center 的第二份业务规则正文，也不定义服务端接口语义。服务端权威规则分别位于 [UC-AUTH-006](../use-cases/UC-AUTH-006-create-user.md)、[UC-AUTH-007](../use-cases/UC-AUTH-007-login.md)、[UC-AUTH-008](../use-cases/UC-AUTH-008-revoke-own-session.md) 和 [UC-AUTH-009](../use-cases/UC-AUTH-009-revoke-own-credential.md)。客户端可调整页面和提示文案，但不能绕过这些用例的认证、授权和失败语义。

## 本地状态边界

客户端按本机账号分别保存 credentialId、由系统安全存储保护的私钥、当前 Session token、本地学校账号引用和账号隔离的数据目录。私钥不进入普通文件、偏好设置、日志、分析事件或业务备份；服务端永远拿不到私钥，也无法证明客户端是否真的完成删除。

账号切换只改变当前交互账号，不等于退出，不应删除另一个账号的私钥。每个后台任务在创建时绑定 authId；切换后不能拿新账号 Session 执行旧账号任务。

## 创建与自动登录建议

首次创建平台账号时，客户端在系统安全存储生成新设备密钥，按 UC-AUTH-006 提交公钥证明和必需的学生关联声明。注册页面应说明本机密钥丢失后的恢复限制；邮箱等恢复能力未交付前，不能展示为已经可用。

[UC-AUTH-011](../use-cases/UC-AUTH-011-set-and-activate-email.md)提出在注册页并列提供“一键注册”和“使用邮箱注册”。选择邮箱注册时，直接准备新设备密钥及关联声明，提交无 Session 的邮箱注册提案，验证成功后才建立账号并取得首次 Session；不需要先一键注册。已有账号设置邮箱则携带其有效 Session。

客户端明确区分“未选择任何平台账号的新注册”和“已有账号 Session 失效”。后者先恢复原账号登录，不通过删掉 token 悄悄变成邮箱注册。发验证码后固定页面对应账号与流程；切换账号或改选注册方式时重新发起操作，不能把同一验证码在注册和绑定间复用。若用户明确放弃原账号并选择创建新账号，则使用新的注册流程与设备密钥，并提示旧数据不继承；未知注册结果仍须先按用例恢复确认。

存在有效 Session 时直接复用。Session 到期或失效且本机仍持有当前账号私钥时，可以自动执行 UC-AUTH-007；服务端不会因为自动触发而降低证明要求。客户端同一账号同时只运行一轮登录，多个业务请求等待同一结果；认证拒绝后停止静默循环，依赖故障采用有界退避。自动取得新 Session 不授权自动重放结果未知的业务写命令。

## 账号切换建议

从 A 切换到 B 时，先确认 B 已有可用 Session 或成功完成登录，再切换本地数据上下文；B 登录失败时继续保持 A。是否调用 UC-AUTH-008 撤销 A 的 Session 是客户端产品选择，不由登录接口隐式完成；无论选择哪种方式，都保留 A 的设备私钥，除非用户另外明确退出 A。

服务端不存在跨账号原子“切换”命令。若客户端选择撤销 A 而结果未知，应准确显示状态，不能把 B 登录成功解释为 A 已经远端退出。

## 退出本机账号建议

官方客户端的“退出”建议表示从本机移除该平台账号，而不仅是撤销一个 Session：

1. 明确警告本机私钥将永久删除；若没有已绑定邮箱、其它可用设备或恢复方式，用户可能无法再次进入原账号及其数据，仅用同一学校账号不能找回原 authId。
2. 用户确认后先写入本地退出屏障，停止该账号的新请求和自动登录；迟到的登录响应不得重新保存 Session。
3. 在线时优先调用 UC-AUTH-009 的 RevokeOwnCredential，目标为本机 credentialId。凭据撤销会使引用它的 Session 在随后检查中失效，因此无需为了同一目的再调用 UC-AUTH-008。
4. 使用系统密钥设施删除私钥并验证之后无法再签名，同时删除本地 Session token、credentialId 和账号缓存。App 崩溃或重启后继续本地清理。
5. 服务端确认成功时显示退出完成；网络不可用或结果未知时仍可完成本地删除，但只显示“已从本机移除，服务端撤销未确认”。首版不为了重试而把即将删除的 token 或私钥另存到秘密队列。

如果产品只需要使当前 token 失效并保留本机私钥，应调用 UC-AUTH-008；这个动作不应在界面上伪装成上述“退出本机账号”。客户端删除私钥不是 UC-AUTH-009 成功的服务端后置条件，服务端凭据撤销也不能替代本地删除。

## 会话管理建议（待 UC020 交付）

[UC020 草案](../use-cases/UC-AUTH-020-manage-own-sessions.md)提供同一 authId 的有效会话列表与明确 ID 集合回收；尚未实现，客户端不能提前展示可用操作。页面建议称“有效会话”，展示最近使用/到期时间及“当前会话”标记，不将其称为真实在线设备清单。

选中其他会话后，提交用户所见的具体 Session ID；“回收其他会话”同样只提交所选列表中的非当前 ID。网络重试保持原集合，不自动刷新列表后追加新登录的会话；未知提交结果不显示完成。成功后刷新列表，之后新出现的会话可能是有效设备重新登录。

提示应说明“结束这些会话；保留设备登录凭据，设备可能重新登录”。用户要阻止某个已识别凭据继续登录时，再明确选择 UC009 的凭据撤销，不把两种动作混成一个按钮。相同 credentialId 可帮助分组，但不能推断真实设备名称；关联组其他账号不出现在本页。

## 新设备与恢复建议

新设备不继承旧私钥。用户通过已验证邮箱、旧设备授权或未来支持的其它方式进入原 authId 后，在新设备生成新密钥并新增 credential；没有恢复方式时只能创建独立平台账号，不继承旧数据。

[UC012](../use-cases/UC-AUTH-012-login-with-email.md)把邮箱登录和本机设备授权放在同一次明确操作中：客户端保存新私钥，提交邮箱与公钥，在用户输入验证码时签署专用挑战；成功后保存原 authId 下的 credentialId 和 Session。旧设备不可用时不需要先取得 Session，也不重新提交学校关联。响应不确定时保留这把私钥，按 UC012 尝试设备登录恢复，不换密钥重复注册。邮箱更换不自动移除既有设备。

从服务端撤销某条凭据不删除其它设备凭据、USER、资料或学生关联。客户端不把 associationToken、学校账号登录成功或相同学号当作恢复旧账号的证明。

## Developer 申请建议

[UC013 草案](../use-cases/UC-AUTH-013-apply-for-developer.md)要求已激活邮箱且邮箱登录能力已完整交付。申请页可先查询本人资格，缺邮箱时引导设置，满足条件后由用户明确申请；不要求退出当前设备 Session 或先完成一次邮箱登录。首版草案为自助开通，成功后复用当前 Session 访问开发者功能，应用审核仍独立进行。上述能力未交付前，不把它们显示为可用能力。

## 仍待客户端验证

- Android/iOS 安全存储的生成、签名、删除、App 重装和系统备份行为。
- 退出警告的最终文案，以及如何展示邮箱/其它设备等恢复能力；不能把无法确认的恢复方式显示为可用。
- 自动登录与网络退避、并发请求合并、App 崩溃恢复和迟到响应测试。
- 多账号数据目录、后台任务和通知点击后的 authId 隔离。
